# 1.0 서문
- 이름 있는 IT 기업들이 실력 있는 개발자를 가려내려고 실시하는 코딩테스트
- 코딩테스트는 무엇이고, 왜 이를 여러 IT 기업에서 중요하게 생각하는지
---
# 1.1 코딩테스트란?
- 코딩 테스트 : 지원자가 알고 있는 자료 구조와 알고리즘 등을 이용하여 문제를 해결해나가는 능력을 평가하는 시험
- 이 테스트를 통과한 지원자만 다음 단계인 면접으로 넘어갈 수 있다.
	![[Frame 77.png|164]]
- 코딩 테스트는 제한 시간 내 기업에서 출제한 몇 개의 문제를 해결하는 코드를 작성해야 한다.
- 출제되는 문제 개수와 난이도는 기업별로 다르지만 일반적으로 4~5문제를 3시간 정도 내 해결해야 하며 문제 난이도는 프로그래머스 기준으로 2~4 레벨 정도이다. 물론 이것은 기업 재량이기때문에 7문제를 5시간에 해결해야 하는 코딩 테스트 등 문제 개수와 시간은 다를 수 있다.

---
# 1.2 코딩테스트를 보는 이유
- 기업이 코딩테스트를 보는 이유는 개발자의 실력은 기능을 구현하기보다 어떻게 효율적으로 설계할 수 있는지 판가름난다.
- 요구 조건에서 제시한 기능을 그대로 구현하는 것은 개발자의 필수 요건이다.
- 구현이 빠르면 좋지만, 코드가 번잡하고 비효율적이라면 절대 실력 있는 개발자라고 할 수 없다.
- 서비스 규모가 작을 때 처음 몇 개의 기능을 별 문제없이 작동될 수 있어도 서비스가 커지고 추가해야 하는 기능들이 늘어날 수록 기존 코드가 발목을 붙잡는 일이 많아지게 될 것이다.
- 개발자의 능력은 기능을 빠르고 많이 만드는 것이 아니라 정확하고 효율적으로 만드는 것이다.
- 코딩 테스트만으로 이런 능력을 전부 확인할 수는 없다. 하지만 코딩 테스트를 통과하려면 코드 효율성을 고려하며 코드를 작성해야 한다. 따라서 코딩 테스트를 준비하는 과정에서 개발자에게 필요한 최소한의 역량이 갖추어지기에 코딩 테스트를 충분히 준비한 개발자를 선호하는 것이다.
## 1.2.1 문제 해결 과정을 보는 것
- 코딩 테스트에서는 주어진 문제를 이미 알고 있는 알고리즘과 자료 구조를 응용해서 해결해야 한다.
- 이 과정에서 개발자에게 필요한 문제 해결 과정을 엿볼 수 있다.
- 먼저 개발자는 주어진 문제를 정확하게 파악해야 한다. 필요한 기능이 주어졌는데 이를 잘못 이해하고 개발을 진행한다면 아무것도 해결하지 못하고 시간만 날리는 셈이다. 코딩 테스트에서는 시간 제한이 있기 때문에 정확하게 파악하지 못한다면 시간 내에 문제를 충분히 풀 수 없다. 따라서 끊임없이 문제에서 요구하는 방향으로 문제를 해결하고 있는지 생각해야 하며, 이는 개발자의 문제 파악 능력을 확인하는 데 도움이 된다.

## 1.2.2 똑같은 결과를 빠르고, 효율적으로
- 아무리 문제에서 요구하는 정답을 구할 수 있는 코드라고 하더라도 효율적이지 못하면 좋은 코드라 할 수 없다.
- 코딩 테스트에서는 문제를 푸는 시간 외에도 실행 시간에도 제한이 있다.
- 비효율적인 코드는 시간 초과로 판정되어 문제를 해결하지 못한 것으로 간주된다. 
- 이처럼 효율적으로 코드를 작성하는 것은 실제 개발할 때는 물론, 코딩 테스트에서도 굉장히 중요하다.

# 1.3 코딩과 디버깅
- 코딩 테스트도 결국은 코드를 작성하는 것이다. 따라서 코드를 작성하는 능력이 좋을수록 유리하다.
- 문제 풀이를 더욱 빨리 구현할 수 있고 실수도 줄어들기 때문이다.

## 1.3.1 잘 짠 코드란?
- 실수 없이 문제를 빠르게 풀려면 코드를 잘 작성하는 것도 중요하다. 물론 가장 먼저 문제를 해결 할 수 있어야 한다. 그렇지 않으면 잘 짠 코드, 잘 못 짠 코드를 구분하기 이전에 이미 틀린 코드이다.
- 잘 짠 코드를 논할 때 개인적으로 가장 중요한 것은 가독성과 효율성이라고 생각한다.
- 읽기 쉬운 코드는 로직에만 집중할 수 있으므로 이해하기 쉽고, 실수가 있어도 쉽게 잡아낼 수 있기 때문이다. 코드를 가독성 있게 작성하면 이후 면접 과정에서 코딩테스트 관련 질의 응답에서도 좋은 인상을 심어줄 수 있다.
- 또, 아무리 읽기 쉬운 코드라고 하더라도 효율성이 떨어진다면 코드를 사용하는 데 어려움이 있다.
- 가독성을 높이고 싶다면 코드 역할에 집중하여 작성해야 한다. 하나의 코드가 너무 많은 역할을 하게 되면 코드가 복잡해지고 가독성이 떨어진다. 따라서 코드가 길어지거나 중복되는 부분이 발생한다면 변수와 메서드, 클래스를 적극적으로 활용하여 읽기 쉬운 코드를 작성할 수 있도록 하고, 역할에 맞게 이름을 붙여 로직에 집중할 수 있도록 해야 한다.

## 1.3.2 코드를 짤 때 흔히 하는 실수들
- 코딩 테스트 문제들은 여러 조건이 있다. 이를 코드로 작성하다 보면 하나의 요구 조건을 처리하는 중에 다른 요구 조건을 신경쓰게 되면서 원래 구현하려고 했던 내용은 잊게 되거나 중간에 구현이 달라 처음부터 다시 구현해야 하는 경우가 빈번히 발생한다.
- 비단 코딩 테스트 뿐만 아니라 프로젝트를 할 때도 막히는 경우가 있을 것이다. 이때 흔히 엎고 다시하라라고 얘기한다.  실제로 모든 코드를 지우고 처음부터 다시 구현하면 정상적으로 동작할 때가 많다. 이것은 단순히 처음 코드를 작성할 때 실수했기 때문만은 아니다.
- 처음 코드를 작성할 때 충분한 설계없이 프로젝트를 시작하면 어떤 기능들이 구현되어야 하는지 정확한 이정표가 없는 채로 코드를 작성해야 한다. 이 상태로 프로젝트를 진행하다 보면 미처 생각하지 못한 것이 발견되어 이를 해결하는 로직을 계속 추가하게 된다. 이때 역할과 가독성을 충분히 고려하지 못한 채로 이것이 누적되면 결국 읽기 어렵고 실수해도 찾기 어려운 코드가 되는 것이다. 이후에 프로젝트를 엎고 다시 시작하면 이미 어떤 기능들에 어떤 데이터와 로직이 필요한지 경험했기에 상대적으로 실수가 적고 더욱 잘 설계된 코드를 작성할 수 있다.
- 개인적으로 프로그래밍을 접한지 얼마 되지 않았거나 설계에 약하다면 프로젝트를 자주 엎으면서 설계를 연습해보기 추천한다
- 코드를 작성할 때 가독성과 역할에 신경쓰면 문제를 단계별로 나누어 해결할 수 있다. 이처럼 코드를 나누어 부분별로 작성하면 이런 실수를 크게 줄일 수 있다.

## 1.3.3 디버깅과 시행착오 줄이기
- 풀이를 제출한 후 정답이 뜨지 않으면 어디에서 오답이 나왔는지 디버깅해야 한다. 이때도 가독성 있게 작성하는 것이 매우 큰 도움이 된다. 가독성 있게 작성된 코드는 문제를 단계별로 해결한다. 이때 각 단계를 검증하는 것으로 디버깅 시간을 줄일 수 있다.
- 이렇게 단계별로 검증하는 과정은 전체 코드를 작성하기 전에도 가능하다. 하나의 단계를 완성하고 예시 입출력으로 검증하며, 다음 단계를 완성하고 검증하는 방식을 사용한다. 이 문제를 해결하기 전에 각 단계가 모두 검증되어 오답을 겪는 시행착오를 줄일 수 있다.
- 디버깅 방법 정리
	1. 코드를 단계별로 작성하기
	2. 하나의 단계를 작성한 후 로그를 찍어 보며 검증하기
	3. 단계 검증이 실패하면 검증이 실패한 단계 내에서 더욱 자세히 로그 찍어보기
